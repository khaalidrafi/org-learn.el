* Goal

Gemini's Guided Learning turns a goal plus the learner's material into
an ordered PLAN: foundations first, a few milestones, each decomposing
into tasks, adapting to what the learner already has.  org-learn's
version, per the DoE notice's own mapping: from a GOAL + NOTES generate
an Org plan — a roadmap-shaped TODO tree (root, milestones, tasks) —
that FLOWS INTO THE EXISTING org-roadmap machinery with zero new
rendering: =org-roadmap-get-todo-tree= / the 0-arg
=org-roadmap-progress= API parse it (spec 011's real-dependency law),
=org-learn-plan-from-roadmap= (org-learn-roadmap.el:287) turns its
milestones into :drill: review items, and =org-learn-progress-report=
(org-learn-roadmap.el:477) writes :LEARN_PROGRESS: onto its nodes.  The
core generator is DETERMINISTIC (no network, pure grouping of the
learner's own note headings — the honest scaffold); an optional AI
decomposition rider (queued, below) re-titles and re-orders the
milestones through the single choke point.  Text-to-speech, mind maps
and the study kit are other DoE items — deliberately OUT of scope here
(specs 013/014 own those lanes).

* Plan format law (pinned Org shape)

The generated plan is a roadmap-shaped TODO tree — the same shape the
roadmap.sh import produces (tests/support/org-roadmap-stub.el:122-133)
so every org-roadmap parser consumes it:

#+begin_src org
* TODO Plan: Learn Org mode
  :PROPERTIES:
  :GOAL: Learn Org mode
  :SOURCE: subtree
  :END:
** TODO Milestone 1: Org syntax
*** TODO Org syntax
*** TODO Headings and stars
*** TODO Capture
** TODO Milestone 2: Review scheduling
*** TODO Review scheduling
*** TODO Drill sessions
# Generated by org-learn plan (spec 015) from subtree.
#+end_src

- Root: =* TODO Plan: <GOAL>= with a =:PROPERTIES:= drawer carrying
  =:GOAL: <goal>= and =:SOURCE: <label>=; the SOURCE vocabulary is
  CLOSED — =subtree= or =org-learn-file= (which topic branch won).
- Milestones: =** TODO Milestone N: <first topic of the cluster>=
  (level 2 = the org-roadmap milestone/topic level the bridge's
  topic-level law consumes).
- Tasks: =*** TODO <topic>= (level 3, the topic title verbatim).
- Footer: exactly one blank line, then the Org comment
  =# Generated by org-learn plan (spec 015) from <label>.= (honesty:
  the buffer states its origin, the spec 013/014 footer law).
- No dates, no SCHEDULED/DEADLINED (scope cut, below).  No :ID: (the
  study-kit's org-id law is spec 014's; a plan is a draft until saved).

* Topic source law (deterministic, ordered)

The core selects topics WITHOUT any network, in this pinned order:

1. SUBTREE branch — when the current buffer is Org and point is on a
   heading: the titles of every heading STRICTLY inside the subtree
   (level greater than point's heading level; the root itself
   excluded), in document order, trimmed, deduplicated (first
   occurrence wins).  Non-empty -> source label =subtree=.
2. NOTES-FILE branch — otherwise: the TODO-state heading titles of
   =org-learn-file= (org-learn.el:56; missing file -> nil), document
   order, trimmed, deduplicated.  Non-empty -> source label
   =org-learn-file=.  This reads the learner's existing capture corpus
   — the same titles =org-learn-plan-from-roadmap= later matches for
   idempotence, so a plan generated from notes drills exactly what the
   learner already captured.
3. Both empty -> =user-error= "org-learn: no notes to plan from (no
   subtree topics and no org-learn-file)".

The CAP law (cognitive-load management, LearnLM principle — DoE notice
TODOS.org:33-34): after selection, when the topic count exceeds
=org-learn-plan-max-topics= (defcustom, default 40), the list is
truncated to the cap and the command messages
="org-learn: plan capped at %d topics"= — a 500-heading subtree must
never become a 167-milestone plan.

* Milestone grouping law (pure)

=org-learn-plan--milestones (topics)= — pure, table-driven:
partition TOPICS into consecutive chunks of
=org-learn-plan-milestone-size= (defcustom, default 3, integer >= 1;
the pure function guards =(< 0 size)= else =user-error= "org-learn-
plan-milestone-size must be >= 1").  Milestone i's title is
=(format "Milestone %d: %s" (1+ i) (first-topic-of-chunk-i))=; its
tasks are the chunk's topics verbatim.  The last chunk may be smaller.
Empty topics -> nil (the source law already guards upstream).  Seven
topics at size 3 -> milestones (3, 3, 1) — the pinned test case.

* Render law (pure)

=org-learn-plan--render (goal source milestones)= returns the complete
buffer text, byte-exact per the format law above:

- root line =(format "* TODO Plan: %s" goal)=; drawer lines
  ="  :PROPERTIES:"=, =(format "  :GOAL: %s" goal)=,
  =(format "  :SOURCE: %s" source)=, ="  :END:"=;
- per milestone =(format "** TODO Milestone %d: %s" (1+ i) title)=
  then per task ="*** TODO %s"=;
- footer: one blank line then
  =(format "# Generated by org-learn plan (spec 015) from %s." source)=.

The renderer takes the milestone ALREADY-TITLED structure (the grouping
law's output) so AI-decomposed milestones (rider, below) render through
the same pure function — the rider changes the grouping, never the
format.

* Core law

   the plan".  No buffer is touched before this passes (no-litter law).
2. Topics via the source selection law above; label recorded.
3. Cap law applied (truncate + message).
4. =milestones = (org-learn-plan--milestones topics)=.
5. =text = (org-learn-plan--render goal label milestones)=.
6. Buffer: =(get-buffer-create org-learn-plan-buffer-name)=,
   =erase-buffer= (reset law — every generation replaces the previous
   plan, the spec 013/014 buffer law), insert, =org-mode=,
   =(goto-char (point-min))=.  Return the buffer.  NO window operations
   in the core (batch-safe; ERT drives it directly — the spec 013
   testability law).

* Interop laws — the DoE "flow" sentence, made testable

The DoE notice pins "milestones that flow into the real
org-roadmap-progress API".  Three flows, all reusing DELIVERED code:

- DRILL FLOW: =org-learn-plan-from-roadmap= (org-learn-roadmap.el:287)
  over the generated plan creates ONE :drill: review item per
  MILESTONE (level-2 = the topic-level law, defcustom :76), titled
  with the milestone text (=Milestone N: <topic>=), carrying
  :LEARN_SOURCE: roadmap and reset LEARN_* properties (:272-285),
  idempotent on re-run (:262).  Level-3 tasks are NOT drilled — the
  topic-level law reads level 2; the milestone is the drillable
  commitment, its tasks are the steps (a future amendment may tag
  tasks; declared here so it is a conscious cut, not an oversight).
- PROGRESS FLOW: =org-learn-progress-report= (org-learn-roadmap.el:477)
  with the plan buffer current and point on the root writes
  :LEARN_PROGRESS: onto every plan node (--write-progress :395) and
  renders the read-only report; the rollup runs through the REAL
  =org-roadmap-progress= whenever that API is bound (the seam :235-242,
  --progress-rollup :243-259 records =rollup: org-roadmap= vs =local
  fallback=).  With no review stats yet the report shows the designed
  fallback line "no review items yet (plan first)" (:411) — planning
  and reviewing are one loop.
- REAL-API FLOW: the 0-arg =org-roadmap-progress= (spec 011's law;
  stub mirror tests/support/org-roadmap-stub.el:153) parses the CURRENT
  buffer — the generated plan buffer — and returns the milestone
  progress alist.  A fresh plan yields the root cell =(0 .
  <task-count>)=; marking tasks DONE and re-running increments the
  done half.  This is the literal "flow into the real
  org-roadmap-progress API".
